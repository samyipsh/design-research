Upload flows explained

Companion to the notes 04 Browser Uploads in Practice, 06 UploadThing: What It Actually Is and 08 Decision: Own Bucket vs UploadThing. As of 2026-10-18. Pick a flow, then step through it. The numbered list under each diagram is the full explanation, and the diagram is its map.

Control: a request that decides or records something Reply: a response on the control path DATA: the file's bytes moving Check: work done inside one box

A · Proxy through your server

Good forSmall files on a long-running server; files your server generates; admin tools. Your server sees the real bytes, and stores exactly what it checked. No browser-to-storage CORS or presigned URLs are needed (your server's SDK still signs its own storage requests).
CostsBytes cross your server twice. Serverless body limits (Vercel Functions: 4.5 MB, then 413). Memory and timeouts. You still have to reconcile a storage write whose DB write failed.

On small screens, scroll the diagram sideways.

  1. dataThe browser sends the whole file to your endpoint as a form upload.Serverless platforms cap request bodies. Vercel Functions reject bodies over 4.5 MB.
  2. checkYour server authenticates the user and can inspect the actual bytes (size, magic bytes) before storing anything. This is the main advantage of proxying.
  3. dataYour server writes the file to the bucket through the storage SDK, which signs the request with your server's credentials. The bytes travel a second time.
  4. replyStorage confirms the write. Your server knows it finished, but still has to record it.
  5. controlYour server records the file (owner, key, verified size and type) as ready.If this fails after the storage write (crash, DB error), the object is an orphan. You still need reconciliation or cleanup.
  6. replyThe browser gets the file's ID.

B · Direct to your bucket (presigned URL)

Good forMost user uploads. Your server stays on the control path only. The core flow uses operations most S3-compatible providers document (check presigned POST and conditional-header support per provider).
You buildSign, finalize and accept steps, bucket CORS, lifecycle rules, and a sweep for abandoned uploads. Agents can draft this from well-documented patterns. You still review it and run it.

On small screens, scroll the diagram sideways.

  1. controlThe browser asks to upload, sending the file's claimed name, size and type.These are claims. The browser can lie.
  2. checkYour server authenticates the user, checks this user may upload this kind of file, applies limits to the claim, and rate-limits.
  3. controlYour server creates a pending row with a server-generated upload key (e.g. incoming/01J9…), so every signed upload is traceable.
  4. checkYour server signs a short-lived PUT (or, on AWS, a POST whose policy adds a size range) for exactly that key, not a whole prefix. The signing is local, though fetching or refreshing the credentials may need a network call. Prefer scoped, temporary credentials.The URL is a reusable bearer permission until it expires, so keep expiry short. R2 documents no presigned POST, so enforce size at finalize there.
  5. replyThe browser receives the URL (and form fields if using POST).
  6. dataThe browser uploads the bytes straight to the bucket, sending a CORS preflight first when the request needs one.If it fails in the browser but works with curl, the bucket's CORS rules are a good first check. They're not the only possible cause.
  7. replyStorage confirms (PUT returns 200; POST may return 204 or 201 depending on configuration). It doesn't tell your server anything.
  8. controlThe browser tells your server it's done.It may never arrive (closed tab), which is why lifecycle expiry and the sweep exist.
  9. controlFinalize: HEAD shows the object exists, its real size and its stored metadata (the declared type, which proves nothing). Reading the first bytes checks the actual format. On S3 this works immediately after upload (strong consistency since 2020).
  10. controlAccept: publish the exact validated snapshot or image derivative to a server-controlled key like files/01J9….Pin a version or use matching conditional reads and copying. Checking a mutable key and copying its latest contents still races with another upload. See note 04 §4. Create-only or checksum-pinned uploads are alternatives where supported.
  11. controlThe row becomes ready and points at the accepted key. If checks failed, it's marked rejected. Finalize and accept should be idempotent.
  12. checkA lifecycle rule expires leftovers under incoming/ after a day and aborts abandoned multipart uploads. A scheduled sweep marks stale pending rows as abandoned.

C · UploadThing v7

What it removesSigning details, the completion signal (signed callback), resumable uploads, upload UI components, and (as advertised) separate bandwidth billing.
What changesFiles go to UploadThing-managed storage (default AWS us-west-2), not a bucket you configure, and are served from <APP_ID>.ufs.sh. Your callback endpoint must be publicly reachable. Bring-your-own-bucket, self-hosting and bulk export aren't documented as of 2026-10-18, which isn't proof they're impossible.

On small screens, scroll the diagram sideways.

  1. controlThe browser calls your /api/uploadthing route for a named file route, with the file's claimed name, size and type.
  2. checkYour middleware runs your authentication. The route config checks type, size and count.The SDK matches type using the browser-supplied MIME (falling back to the filename), with no byte inspection.
  3. checkYour server signs an ingest URL (HMAC-SHA256 with your UploadThing API key) covering file key, name, size, route and expiry. A size mismatch makes the upload fail.
  4. controlYour server registers the file keys, metadata and callback URL with the ingest service.
  5. replyThe browser receives the signed URL.
  6. dataThe browser uploads to {region}.ingest.uploadthing.com. Interrupted uploads can resume.The docs don't say whether a signed ingest URL can be reused after the upload completes.
  7. dataIngest writes the file to UploadThing-managed storage in your app's region.Changing region later doesn't move existing files.
  8. controlUploadThing calls your endpoint with an HMAC-signed body. The SDK verifies it.Localhost needs a tunnel for production-like tests, and Vercel preview protection blocks callbacks unless bypassed.
  9. controlYour onUploadComplete records the file in your DB (key, owner, purpose). UploadThing's docs recommend keeping file data in your own DB.
  10. replyWith awaitServerData (the default), your result goes back through ingest…
  11. reply…to the browser, which finishes the upload call.
  12. dataLater reads come from UploadThing's storage and CDN. Private files need a short-lived signed URL (a paid-plan feature).The two paths depend on different parts. New uploads need the ingest service and your callback endpoint. Reads need UploadThing's storage and CDN. In the 2024-09-10 incident, file URLs were unreachable for 53 minutes while the stored files stayed intact.
